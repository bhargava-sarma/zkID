# Issuer research (Phase 1)

What UIDAI actually issues today, whether an "18 or older" proof can be built on
it in a browser, and what the law says. Written 2026-10-20 for the Phase 1 stop
gate. Go/no-go is in [section 9](#9-go--no-go).

**How to read the sources.** Every claim is tagged:

- **[P]** primary source read directly (UIDAI, Gazette text, government press release, Anon Aadhaar source code for claims about Anon Aadhaar);
- **[P-copy]** a primary document obtained through a copy, because the original host was unreachable;
- **[S]** secondary source (law firm, news, Anon Aadhaar's description of UIDAI's format);
- **[M]** measured in this repository, with the script named.

**Access limits.** From this build environment `uidai.gov.in`,
`myaadhaar.uidai.gov.in`, `egazette.gov.in` and `web.archive.org` were
unreachable (connection resets, HTTP 503, TLS errors). UIDAI's developer
documentation at `docs.uidai.gov.in` was reachable. So several UIDAI pages
(the Secure QR reader page, the current certificate list, the December 2025
consolidated regulations, the 30 April 2026 circular) were **not read**. Where
that matters it is said below, and [section 10](#10-open-items-for-the-owner)
lists what the owner should fetch from an Indian network.

## 2. What UIDAI issues in 2026

### 2.1 Aadhaar Secure QR

A QR code "generated by the Authority which contains digitally signed data like
last 4 digits of Aadhaar number, demographic data like name, address, gender,
and date of birth, and photograph" (Regulation 2(bc)) [P-copy, ref 8]. It is
printed on the Aadhaar letter, e-Aadhaar and the PVC card (Regulation 2(bd),
16B(1)) [P-copy, ref 8]. The holder can download e-Aadhaar (a PDF carrying the
code) themselves; the regulations say UIDAI "shall provide various means to
download QR Code, e-Aadhaar or Aadhaar Paperless Offline e-KYC" (Regulation
3A(2)) [P-copy, ref 8]. With the offline e-KYC XML (2.2, not pursued), it is
one of the two UIDAI-signed artefacts found that a holder can obtain themselves
and feed to an arbitrary app without the verifier being registered with UIDAI.

### 2.2 Aadhaar Paperless Offline e-KYC (XML)

A digitally signed XML document (Regulation 2(bb)) [P-copy, ref 8]. Not pursued;
see U4.

### 2.3 Aadhaar Verifiable Credentials (AVC): new in 2026

UIDAI's developer documentation [P, refs 1–4] defines two formats held by the
new Aadhaar App:

- **SD-JWT VC** (RFC 9901): header `alg: ES256`, `typ: vc+sd-jwt`, `kid` into a
  UIDAI JWKS. Payload carries `iss`, a per-credential UUID `id`, `iat`, `exp`, a
  `status` URL (`pehchaan.uidai.gov.in/credentials/status/<id>`), and `cnf`, a
  P-256 holder key. Claims are salted-hash disclosures and include
  **`AgeAbove18`** ("Is age above 18 years?"), selectively disclosable.
- **ISO 18013-5 mDoc**: CBOR, COSE_Sign1 over a Mobile Security Object, device
  key binding, default validity one year.

The documentation is not internally consistent: the sample SD-JWT in the
credential-exchange pages has header `{"alg":"RS256","typ":"sd-JWT"}`, an
`issuer: "UIDAI"` field and no `cnf`, `exp` or `status` [M on the doc's sample,
claim names only]. The production profile was not observed.

How a verifier gets one [P, refs 3–4]: the verifier's request JWT must carry
`ac`, "a unique code for the AUA which is assigned by UIDAI", and is signed with
the verifier's own key. The Aadhaar App sends the request to UIDAI's backend to
check that signature, asks the holder for **FaceAuth**, and posts the SD-JWT to
the verifier's callback. UIDAI declared these credentials valid proof of
identity on a par with e-Aadhaar (PIB, 12 May 2026) [P, ref 11], and reported
100 entities onboarded as OVSEs within three months of roll-out (PIB, 20 April
2026) [P, ref 10].

What this means for zkID:

| Property | Secure QR + ZK | AVC as UIDAI ships it |
|---|---|---|
| Authority signature | RSA-2048, verifiable in-circuit | ES256 (P-256); not attempted in-circuit here |
| Verifier binding (G2) | only what our protocol adds | yes: nonce, state, `jti`, short expiry |
| Minimal disclosure (G5) | yes, via ZK | yes for `AgeAbove18`, but every presentation also carries `id`, `cnf` and the issuer signature |
| Unlinkable across sites (A5) | yes, if the nullifier material stays secret (section 6) | **no**: `id`, `cnf` and the signature are the same at every site |
| Per-site uniqueness (G3) | photo-based nullifier, with limits | not provided |
| Lending (A3) | not defended | FaceAuth at presentation |
| Who learns of each verification | nobody | UIDAI's backend checks each request |
| Who can use it | anyone with the code | UIDAI-registered entities only |

So AVC is not a better input for this project: a third-party app cannot obtain
it without UIDAI registration, and it already gives verifier binding and
minimal disclosure natively. ZK adds unlinkability and per-site uniqueness,
which only matter if the input is Secure QR.

## 3. Secure QR in detail

All [M] results come from `spike/secure-qr` (`npm test`, `verify-qr.mjs`).

### 3.1 Encoding and signature

| Step | UIDAI official sample (V1) | Anon Aadhaar test code (V2, test key) |
|---|---|---|
| QR text | 3,181 decimal digits | 3,169 digits |
| Compressed | 1,321 bytes, **gzip** (`1f 8b 08`) | 1,316 bytes, zlib (`78 9c`) |
| Decompressed | 1,385 bytes | 1,393 bytes |
| Signed data | **1,129 bytes** | 1,137 bytes |
| Signature | last 256 bytes; RSASSA-PKCS1-v1_5 / SHA-256 | same |
| Verifies under | **UIDAI "DS UIDAI 4"** (2017-06-08 to 2020-06-07); not under the 2021 or 2024 keys | Anon Aadhaar's test certificate |
| One flipped bit (data or signature) | rejected | rejected |

UIDAI's sample is the "official test data" UIDAI published on its QR reader page
[S: Anon Aadhaar's `scripts/generateTestData.ts`, ref 6]. It was generated on
2019-03-08, inside that key's validity window. It contains a sample resident's
details, so it is fetched to a gitignored directory
(`npm run fetch-uidai-sample`) and never committed.

### 3.2 Field layout

| # | V1 [M] | V2 [S, ref 6] |
|---|---|---|
| prefix | none | `V2`, then 0xFF |
| 1 | email/mobile indicator (0–3) | same |
| 2 | reference ID (21 digits) | same |
| 3–5 | name, DOB (`DD-MM-YYYY` [M: pattern only]), gender (1 letter) | same |
| 6–16 | care of, district, landmark, house, location, PIN, post office, state, street, sub-district, VTC | same |
| 17 | (none) | last 4 digits of mobile |
| then | photo: JPEG 2000, **888 bytes** in the sample, starting `FF 4F FF 51`, ending `FF D9` | photo |
| then | **64 bytes**: mobile and email SHA-256 hashes (indicator 3) | described as removed |

The photo itself contains 0xFF bytes, so a parser must count the text-field
delimiters and not split the whole buffer on 0xFF.

Anon Aadhaar's V2 test data was made by converting UIDAI's V1 sample. It still
carries the 64 hash bytes after the photo [M], although its own notes say V2 has
none. Its test vector is therefore not exactly a V2 code, and nobody here has
seen a real V2 code. `verify-qr.mjs` reports the bytes after the photo so the
owner's real code settles this.

### 3.3 Signed message size

| Source | Signed bytes | SHA-256 blocks (64 B) |
|---|---|---|
| UIDAI V1 sample [M] | 1,129 | 18 |
| Synthetic V2, 888-byte photo [M] | 1,077 | 17 |
| Anon Aadhaar's circuit bound [P] | ≤ 1,536 (padded) | ≤ 24 |

The size is dominated by the photo. The distribution of real photo sizes is
unknown; Anon Aadhaar's 1,536-byte bound has held for its users, which is
indirect evidence only.

- SHA-256 `E0:30:4B:9E:61:EE:36:40:EC:DD:AE:2D:B4:B6:17:F2:E2:67:8F:57:DB:C2:82:6C:2F:86:AC:5C:04:F2:77:DF`;
- download link
  `https://backend.uidai.gov.in/get/files/media/document/2026-07/uidai_offline_publickey_2026.cer`,
  which also resets connections from this environment.

By name it is the "offline" key, which UIDAI uses for both the Paperless
Offline e-KYC XML and Secure QR.

Consequences for the design:

- The **public key must be a circuit input** (as in Anon Aadhaar), checked
  against a registry outside the circuit, and not a constant.
- A signature made while a key was valid stays valid after the certificate
  expires, so old codes keep verifying. The registry should store each key's
  validity window, and the verifier should require the code's generation time
  to fall inside the window of the key that signed it.
- Rotation already breaks existing verifiers. At commit `4dad918`, Anon
  Aadhaar's `core.verify()` accepts exactly one key hash, the 2021–2024 key [M:
  Poseidon key hash recomputed for all three certificates]. Its React SDK
  accepts QR signatures under both the 2021 and the 2024 key. So a code signed
  by the 2024–2026 key passes the SDK's pre-check, but its proof fails
  `core.verify()` with "public key mismatch". It never checks the timestamp
  against the key's window.
- **The key signing codes downloaded today is unknown.** The owner needs to
  fetch the current certificate from UIDAI's Secure QR reader page, or check a
  freshly downloaded e-Aadhaar with `verify-qr.mjs` and see whether any known key
  verifies it.

## 5. Anon Aadhaar (prior work)

Anon Aadhaar (PSE; repository `anon-aadhaar/anon-aadhaar`, read at commit
`4dad918`, 2025-04-19) already proves statements about Secure QR codes in the
browser [P, ref 6]. What it does:

- **Circuit** `AadhaarQRVerifier(121, 17, 1536)`: SHA-256 over the padded
  signed data, then RSA (`RSAVerifier65537`). Delimiter positions are prover
  hints, validated by rewriting the n-th delimiter as n × 255. It extracts the
  timestamp (to the hour, converted from IST to Unix), DOB, gender, PIN code,
  state and photo.
- **Public inputs**: `nullifierSeed` (per application) and `signalHash` (any
  value the proof commits to).
- **Outputs**: Poseidon hash of the key, nullifier, timestamp, and
  `ageAbove18`, gender, PIN code and state (each 0 unless revealed).
  `ageAbove18` is computed against the code's generation date, not today: "User
  can generate fresh QR for accuracy" (comment in `extractor.circom`).
- **Trusted setup**: the published v2.0.0 proving key (612 MB) has **105 phase-2
  contributions plus a beacon** [M, read from the zkey].
- **Licence**: MIT (as are zk-email's circuits). circomlib, which it and zkID v1
  both include, is GPL-3.0.
- **Audit** (PSE, March 2024) [P, ref 7]: a critical input-ordering bug and an
  age-calculation bug, both fixed. One High finding stays open by design: *"User
  can bypass nullifier by changing photo"*. Its recommendation reads "There is
  no way to avoid this situation."

Overlap with the brief's goals:

| Goal | Already in Anon Aadhaar? |
|---|---|
| G1 authority signature checked in-circuit | yes |
| G2 proof bound to a verifier's challenge | the mechanism (`signalHash`) yes; no challenge protocol or single-use enforcement |
| G3 per-verifier nullifier | yes (`nullifierSeed` + photo) |
| G4 freshness | timestamp output yes; no policy |
| G5 minimal disclosure | yes (reveal flags), but the timestamp (hour precision) is always revealed |
| G6 client-side proving | yes |

What is genuinely left for zkID is the protocol and evidence layer:

- single-use, expiring challenges bound into `signalHash`;
- a verifier SDK with typed failures;
- a key registry with validity windows, including the timestamp-in-window check;
- freshness and nullifier policy;
- the attack suite;
- an honest threat model.

"Nullifier design" should not be claimed unless it improves on Anon Aadhaar's
(section 6). This changes Phase 3; see section 9.

## 6. Nullifier material and its stability

| Candidate | Stable across downloads? | Entropy | Verdict |
|---|---|---|---|
| Reference ID | no: contains the generation time [M] | n/a | rejected (brief says so too) |
| Whole signed data or signature | no: they contain the reference ID | n/a | rejected |
| Name + DOB + gender (+ PIN) | yes, unless updated | low: guessable from public data, so nullifiers could be brute-forced and linked | rejected |
| Last 4 Aadhaar digits | yes | 10⁴ | rejected |
| **Photo (JPEG 2000 bytes)** | **unverified** | high (~888 bytes of compressed image) | best available; Anon Aadhaar's choice |

Known limits of the photo, all of which belong in the threat model:

1. **A photo update gives a new nullifier**, so one more account per site
   (Anon Aadhaar audit, High, no fix) [P, ref 7].
2. **Byte stability is unverified.** Nothing read here says UIDAI encodes the
   photo identically on every download. This is what step 1.3 must measure;
   `spike/secure-qr/compare-downloads.mjs` does it without printing any values.
3. **The material is not secret.** The photo bytes sit in a QR code printed on
   every Aadhaar letter, e-Aadhaar and PVC card, which are routinely photocopied
   for hotels, SIM cards and offices. Anyone who has seen a person's code can:
   - compute that person's nullifier at any site, so linking across sites is
     possible for whoever holds the code;
   - produce valid proofs as that person, because there is no holder binding.
   The nullifier then limits this to one account per site, and the first party
   to use it wins. So an attacker with a photocopy can occupy the victim's slot
   before the victim does.

## 7. Cost (measured)

Scripts and raw output: `spike/circuit-cost/` (`results/`).

**Toolchain.**

- circom 2.2.3 (release binary, sha256 `85342c7f…`), circomlib 2.0.5,
  @zk-email/circuits 6.3.4, snarkjs 0.7.6, Node 22.22.0;
- headless Chromium 141 (Playwright 1.56.1);
- a 4-core Intel Xeon @ 2.10 GHz cloud container with 16 GB RAM.

These are desktop-class numbers on a modest CPU, not a laptop or phone.

### 7.1 Constraints

| Circuit | `--O1` (circom 2.2.3 default) | `--O2` |
|---|---|---|
| SHA-256 `Sha256Bytes(640)` | 333,524 | 315,741 |
| `Sha256Bytes(1152)` | 600,533 | 568,606 |
| `Sha256Bytes(1536)` | 800,789 | 758,254 |
| `Sha256Bytes(2048)` | 1,067,797 | 1,011,118 |
| RSA-2048 `RSAVerifier65537(121, 17)` | 190,945 | 185,903 |
| zkID v1 `CredentialAgeProof(119)` | **256,574** (matches the v1 README and v1 key: R6 check passes) | 248,861 |
| Anon Aadhaar `AadhaarQRVerifier(121, 17, 1536)` @ `4dad918` | 1,152,888 | 1,076,870 |
| same source, circom **2.1.9** + zk-email **6.1.1** (its June 2024 toolchain) | 1,115,080 | **1,040,218**, 1,026,196 wires: **matches the published key** |

- **SHA-256 dominates.** It costs about **33,400 constraints per 64-byte block**,
  so each extra 512 bytes of signed data adds about 267,000 constraints. In
  Anon Aadhaar's circuit (O2):
  - hashing the 1,536-byte bound is about 70%;
  - RSA is about 17%;
  - everything else (field extraction, delimiter checks, photo packing,
    Poseidon nullifier and key hash) is about 12%.
- **The bound is set by the photo.** The signed data must be hashed in full
  whether or not the photo is used. A tighter bound (e.g. 1,152 bytes, saving
  about 190,000 constraints) is only safe once real photo sizes are known.
- **Powers of tau.** The published key uses a 2^20 domain. The same source built
  with today's toolchain needs 2^21 (1,076,870 > 1,048,576). A zkID-built
  circuit (option B) would need the Hermez `pot20` or `pot21` file. Neither could
  be downloaded here (HTTP 403); `pot19` is 604 MB in this repo's `circuit-v1`
  release, and size doubles per power.
- **Reproducibility of Anon Aadhaar's key.** The published proving key matches
  its June 2024 source when built with circom 2.1.9 and @zk-email/circuits 6.1.1
  [M, `results/anon-aadhaar-repro.txt`]. A full `snarkjs zkey verify` still needs
  the Hermez powers of tau.

### 7.2 Proving time and memory

| | Anon Aadhaar v2.0.0 (1,040,218 constraints, 2^20) | zkID v1 age (256,574, 2^18) |
|---|---|---|
| Node: witness | 3.4 s | 1.4 s |
| Node: proof | **34.4 s** (median of 3; 33.4–36.5 s) | 8.3 s |
| Node: peak RSS | 3.8 GB | 1.3 GB |
| Chromium: witness + proof | **51.8 s** (median of 3; 50.3–51.8 s) | not measured |
| Chromium: peak memory, summed over its processes* | **4.6–4.8 GB** | not measured |
| Chromium: main-thread JS heap | 1.85 GB | not measured |

\* Shared pages are counted once per process, so this overstates the true footprint somewhat.

Proving time scales with constraint count: about 4× the constraints, about 4×
the proof time.

**Mobile: not measured.** No device was available. Anon Aadhaar's changelog says
version 2.4.1 enabled "mobile browser proving" [S], without numbers. A browser
needing about 5 GB on desktop is a real risk on a mid-range phone. Phase 3.4
must measure on an actual phone before promising mobile proving.

### 7.3 What Anon Aadhaar's circuit enforces

Checked on synthetic data by witness generation [M, `check_controls.mjs`,
`results/controls.json`]. All 12 checks behaved as listed.

| Input | Result |
|---|---|
| valid synthetic code (DOB 1990) | accepted, `ageAbove18 = 1` |
| one DOB byte or one photo byte changed | rejected (RSA check) |
| one signature bit changed; signature checked under another key | rejected (RSA check) |
| DOB delimiter hint off by one | rejected (delimiter assertion) |
| **holder under 18** | **accepted**, `ageAbove18 = 0` |
| adult with `revealAgeAbove18 = 0` | accepted, `ageAbove18 = 0` |
| same photo, re-downloaded, same seed | same nullifier; different timestamp |
| same code, other seed | different nullifier |
| timestamp output | the generation hour (IST boundary) |

So age is an **output, not an assertion**. A verifier that does not check
`ageAbove18 == 1` accepts minors. The verifier SDK must make that impossible to
forget.

## 8. Law and policy

Read as a technical reader, not legal advice.

**Aadhaar Act, section 8A** (inserted 2019; text from the 2019 Bill [P-copy,
ref 12]; the enacted Act was not retrieved). An offline verification-seeking
entity must:

- obtain consent and use the collected information only for the verification;
- inform the individual of the nature of information shared, its uses, and
  alternatives;
- not subject the holder to authentication;
- not "collect, use, or store an Aadhaar number or biometric information of any
  individual for any purpose".

A Secure QR holds only the last 4 digits, so a zkID verifier never sees the
Aadhaar number.

**Aadhaar (Authentication and Offline Verification) Regulations, 2021**, as
compiled with amendments to 3 December 2024 [P-copy, ref 8, OCR of a scanned
copy]:

- 2(ma), 2(mb): offline verification, OVSE ("any entity desirous of undertaking
  offline verification").
- 3A: QR code verification is an offline verification type "as per the
  specifications given by the Authority".
- 5, 6: inform the holder; obtain consent "in physical or preferably in
  electronic form" and keep records.
- 10(2): the OVSE notifies the holder of each offline verification.
- 14A: OVSE obligations, including not to collect, use or store the Aadhaar
  number.
- 16A(1): use only for the purpose stated. 16A(2): **"No entity shall perform
  Offline Verification on behalf of another entity or person."** So zkID must
  not be a central verification service. Each relying party runs the SDK itself.
- 16B, 16C: an OVSE must verify UIDAI's digital signature in the Secure QR
  before accepting Aadhaar as proof of identity.
- 22(1): OVSE servers used for offline verification must be in India.

**December 2025 amendment** (notified 9 Dec 2025 per secondary sources) [S,
refs 13–14]: adds Aadhaar Verifiable Credentials and offline face verification,
a registration framework for OVSEs, and removes some XML and m-Aadhaar
references. Sources disagree on whether registration applies to plain QR
verification. **Not verified against the Gazette.**

**DPDP Act, 2023** [P, ref 9]:

- section 2(f): a "child" is under 18;
- section 9(1): verifiable parental consent before processing a child's data;
- section 9(3): no tracking or behavioural monitoring of children.

This is the main legal reason Indian services may need age assurance. The DPDP
Rules, 2025 (G.S.R. 846(E), 13 Nov 2025; rule 10 on verifiable consent said to
take effect 13 May 2027) [S, ref 15] reportedly allow age or identity checks via
"virtual tokens" from government-authorised entities such as DigiLocker. Not
read in the original.

**Position.** Whether a relying party that only verifies a ZK proof derived
from a Secure QR is an OVSE, and whether it must register, is **unclear**.
Treat zkID as a **research prototype**: it must not be described as
"deployable" or "compliant". Any real deployment would at least need:

- consent and per-verification notification;
- purpose limitation and verifier infrastructure in India;
- a legal opinion on registration.

## 9. Go / no-go

**Recommendation: GO on the real issuer (Aadhaar Secure QR), with Phase 3
redesigned, under three conditions the owner can meet.**

Why go:

- The format and the signature check are confirmed on UIDAI-signed bytes
  against a UIDAI certificate [M].
- Proving a Secure QR statement in a desktop browser works: 51.8 s and about
  5 GB here, for Anon Aadhaar's 1.04M-constraint circuit (section 7). That is
  slow and memory-hungry but usable on desktop; mobile is unmeasured.
- Secure QR is the simplest UIDAI-signed credential a holder can obtain and
  use with an unregistered app. AVCs need UIDAI registration; the offline XML is
  harder to use and reportedly being phased out of the regulations.

Conditions (open items for the owner, section 10):

1. **Current certificate.** Obtain the certificate signing codes downloaded
   now, and confirm a fresh e-Aadhaar verifies under it with `verify-qr.mjs`.
2. **V2 layout.** Confirm on a real code: field count, the bytes after the
   photo, and that the photo starts at the expected delimiter.
3. **Photo stability.** Run `compare-downloads.mjs` on two downloads made on
   different days. If the photo differs between downloads, a photo-based
   nullifier fails G3 and the design needs another stable, high-entropy
   signed field. None is known.

Redesign Phase 3. Writing "circuit v2" from scratch would mostly re-implement
Anon Aadhaar's audited circuit with a far weaker setup (zkID v1 had one
contribution; Anon Aadhaar has 105 plus a beacon). Two options:

- **A (recommended).** Use Anon Aadhaar's circuit and published proving key
  unchanged, cited as prior work, and build zkID's contribution on top:
  - challenge protocol in `signalHash`;
  - verifier SDK with typed failures;
  - registry with key validity windows;
  - freshness and nullifier policy;
  - holder app;
  - attack suite and threat model.

  Its fixed "18+ at QR generation date" check and hour-precision timestamp
  become documented limitations.
- **B.** Write zkID's own circuit only where it changes a property:
  - a verifier-chosen cutoff, e.g. 21+;
  - a coarser freshness output, to reduce linkability through the timestamp;
  - the key-window check in-circuit.

  B costs about the same constraints (section 7) and needs its own phase-2
  ceremony.

A first, B only if it measurably improves a row of the attack report.

**Fallback** if the conditions cannot be met: keep the issuer pluggable and use
`spike/secure-qr/synthetic.mjs` as a format-faithful **test** issuer (V2
layout, gzip, RSA-2048, ephemeral key). The rest of the protocol stays intact,
and the docs must say prominently that no real credential is verified.

**The thesis needs two qualifiers** whatever the choice:

- "cannot create more than one account per site per credential" fails across a
  photo update;
- "cannot be linked across sites" holds only against parties who have not seen
  the person's QR code.
